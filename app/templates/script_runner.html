Works today — no install, no IT

Set up once per laptop, then a code per run.

96% of an emitted script is embedded JSON — the big GOW one is 651 KB of which 621 KB is payload. So don't carry it through the clipboard. Press Get run code on any script card, then run this loader and type the code. The loader never changes, so save it once and you are done with pasting scripts. Chrome's extension policy does not apply to snippets or bookmarklets.

Set up once — as a DevTools Snippet:

  1. On a backoffice tab: F12 → Sources → Snippets → New snippet.
  2. Paste the loader (button above) and save with Cmd-S. Name it Jugabet Runner.

Every run after that:

  1. In the CRM, press Get run code on the script card and note the code.
  2. On the backoffice tab: F12 → Sources → Snippets → double-click Jugabet Runner.
  3. Type the code into the prompt. Watch the console for the created JRN-… ids.

Try this first — it's one click instead of F12. Drag this link to your bookmarks bar, then click it while on a backoffice tab:

Jugabet Runner

Whether it works depends on the backoffice's Content Security Policy: a bookmarklet is allowed to run, but the eval inside it may not be. If the console says so, use the Snippet instead — DevTools is exempt, which is why pasting works today. Nothing is lost by testing it.

A code is good for {{ ttl_minutes }} minutes and {{ max_reads }} runs, then it dies. The script never leaves the CRM until a code is redeemed, and Copy script is still on every card as the fallback.

The extension route — blocked until IT acts

Confirmed on a company laptop — IT has to push it.

Chrome here is managed by user cloud policy from the Google Admin console, and it is default-deny: ExtensionInstallBlocklist is ["*"], with an ExtensionInstallAllowlist of ~245 ids carving out the exceptions. Ours is not one, so Load unpacked fails with:

Extension installation is blocked by policy.

CloudExtensionRequestEnabled is false too, so Chrome's own "request this extension" button is disabled — it has to be a human ask. ExtensionInstallForcelist overrides the blocklist, though, and your org already uses it for another extension, so the request below is the way in. Option 2 is kept only for a machine whose Chrome is not managed.

Extension, option 1 — ask IT to install it

The only route on a managed laptop. One ticket, then nothing for operators to do, ever.

Ask the Google Workspace admin to add this one entry to ExtensionInstallForcelist in the Admin console — the policy they already populate. A forcelist entry beats ExtensionInstallBlocklist: ["*"], so the id does not also need allowlisting.

Do not put it in cloud ExtensionSettings. On these machines ExtensionSettings is set at platform machine level by the Mac MDM, and Chrome's precedence order — platform machine > cloud machine > platform user > cloud user — means the MDM value overrides the cloud one wholesale. chrome://policy already reports that conflict. An entry added to cloud ExtensionSettings would be silently ignored.

The alternative, for whoever manages the Macs: append this to the existing ExtensionSettings dictionary in the MDM profile (append — replacing it would drop Endpoint Verification). That level has the highest precedence of all.

Extension id
{{ meta.id }}
Update URL
{{ base }}/script-runner/update.xml
Version
{{ meta.version }}
Built
{{ meta.built_at }}

The update URL has to be reachable without a login — Chrome cannot sign in — so that one route is public. It serves only the extension code, which holds no secrets. It is self-hosted rather than a Web Store listing on purpose: the extension runs script text taken from the CRM page, which would likely fail store review as remote code.

Worth telling IT: no blocked_permissions is set anywhere in the current policy, so the debugger permission this extension needs is already allowed. Nothing else has to change.

Extension, option 2 — install it yourself

Only on an unmanaged Chrome. Blocked by policy on company laptops — see above.

Download ZIP
  1. Download the ZIP above and unzip it somewhere permanent — not Downloads, and don't move or delete the folder afterwards. Chrome loads it from that path on every launch.
  2. Open a new tab and go to chrome://extensions (type it — Chrome blocks links to chrome:// pages).
  3. Turn on Developer mode, top right.
  4. Click Load unpacked and pick the unzipped folder.
  5. On the new Jugabet Script Runner card, click Details → Extension options, add this origin, and click Allow when Chrome asks:
    {{ crm_origin_pattern }}
  6. Reload this CRM tab.

One catch. Chrome nags about developer-mode extensions on every launch and can switch them off. If the Run in backoffice button disappears, that is why — re-enable it at chrome://extensions. It is the reason Option 1 is worth the ticket.

Using it

What changes once it is installed.

  1. Generate a script as usual, on Optimization or AI.
  2. Press Run in backoffice. The extension's toolbar icon badges the number of queued scripts.
  3. Make sure a logged-in backoffice tab is open, then open the extension popup and press Run.
  4. Read the log in the popup. Created JRN-… ids are pulled out and shown as chips.

Two things that are expected, not faults: Chrome shows a "started debugging this browser" bar while a script runs — that is how the script gets to run in the page exactly as a console paste would, and it clears when the run ends. And Copy script is still on every card; it stays as the fallback whenever a run misbehaves.

Nothing about how scripts are built changes. Verification still happens before a script exists, the extension never builds a payload, and every line the script logs — refusals included — is shown verbatim. A run that stopped early looks stopped.
